## 🔥 Summary: Scope → Execution Context → Hoisting → TDZ → Closures

## JavaScript Runtime Fundamentals — Summary

|  ## | Concept                           | Simple Meaning                                                 | Key Example                                                 | Interview Point                                                        |
| -: | --------------------------------- | -------------------------------------------------------------- | ----------------------------------------------------------- | ---------------------------------------------------------------------- |
|  1 | **Scope**                         | Where a variable can be accessed                               | `let x = 10` inside a function → accessible there           | Determines variable visibility                                         |
|  2 | **Lexical Scope**                 | Scope is determined by **where code is written**               | Inner function can access variables from its outer function | **Where defined**, not where called                                    |
|  3 | **Scope Chain**                   | JS searches from current scope outward                         | `inner → outer → global`                                    | Used for variable lookup                                               |
|  4 | **Execution Context**             | Environment created when JS executes code                      | Global context, then function context                       | Contains information needed to execute code                            |
|  5 | **Function Execution Context**    | New execution context created for each function call           | `foo()` creates a context                                   | Each function call gets its own execution state                        |
|  6 | **Call Stack**                    | Stack that tracks currently executing functions                | `a() → b() → c()`                                           | Last function called is first to finish                                |
|  7 | **Hoisting**                      | Declarations are processed before normal execution             | `console.log(x); var x = 10`                                | Declaration is available before its line executes                      |
|  8 | **`var` Hoisting**                | `var` is hoisted and initialized to `undefined`                | `console.log(x); var x = 10` → `undefined`                  | Declaration hoisted, assignment isn't                                  |
|  9 | **`let` Hoisting**                | `let` is hoisted but unavailable before initialization         | `console.log(x); let x = 10` → `ReferenceError`             | `let` is in TDZ                                                        |
| 10 | **`const` Hoisting**              | Same basic TDZ behavior as `let`                               | `console.log(x); const x = 10`                              | Cannot access before declaration                                       |
| 11 | **TDZ**                           | Period between entering scope and `let`/`const` initialization | `console.log(x); let x = 10`                                | Accessing variable during TDZ causes `ReferenceError`                  |
| 12 | **Block Scope**                   | Scope created by `{}`                                          | `if (...) { let x }`                                        | `let` and `const` are block-scoped                                     |
| 13 | **Function Scope**                | Scope limited to a function                                    | `function foo() { var x }`                                  | `var` is function-scoped                                               |
| 14 | **Closure**                       | Function remembers/accesses its outer lexical environment      | `return () => console.log(x)`                               | Function can access outer variables even after outer function finishes |
| 15 | **Private State**                 | Closure can hide variables from outside code                   | `createCounter()`                                           | Common way to create encapsulated state                                |
| 16 | **Separate Closures**             | Each function invocation can create separate state             | `counter1` vs `counter2`                                    | Each `createCounter()` gets its own environment                        |
| 17 | **Callback**                      | Function passed to another function                            | `setTimeout(fn, 1000)`                                      | Callback and closure are different concepts                            |
| 18 | **Loop + `var`**                  | One shared binding can be captured by all callbacks            | `var i` → `3,3,3`                                           | Classic closure problem                                                |
| 19 | **Loop + `let`**                  | Each iteration gets an appropriate binding                     | `let i` → `0,1,2`                                           | Fixes classic loop closure issue                                       |
| 20 | **Variable Lookup**               | JS searches current scope, then parent scopes                  | `inner → outer → global`                                    | Stops when it finds the variable                                       |
| 21 | **Garbage Collection & Closures** | Captured variables can remain alive while reachable            | Returned function uses `count`                              | Closure can extend lifetime of captured data                           |

## 🔥 Scope vs Execution Context vs Closure

| Concept               | Think of it as                          | Main Question                                          |
| --------------------- | --------------------------------------- | ------------------------------------------------------ |
| **Scope**             | Variable visibility boundary            | "Where can I access this variable?"                    |
| **Lexical Scope**     | Scope based on code location            | "Where was this function written?"                     |
| **Scope Chain**       | Search path                             | "Where will JS look for this variable?"                |
| **Execution Context** | Current execution environment           | "What does JS need to execute this code?"              |
| **Call Stack**        | Execution history/stack                 | "Which function is currently running?"                 |
| **Closure**           | Function + remembered outer environment | "What outer variables can this function still access?" |

## 🔥 Closure — Most Important Table

| Step | What happens                                        |
| ---- | --------------------------------------------------- |
| 1    | `outer()` is called                                 |
| 2    | `outer` gets its own execution context              |
| 3    | `outer` creates variables                           |
| 4    | `inner()` is created inside `outer`                 |
| 5    | `inner` has access to `outer`'s lexical environment |
| 6    | `outer()` finishes                                  |
| 7    | `inner` is returned                                 |
| 8    | `inner()` is called later                           |
| 9    | `inner` can still access variables from `outer`     |
| 10   | This behavior is called a **closure**               |

Example:

```ts
function createCounter() {
  let count = 0;

  return () => {
    count++;
    return count;
  };
}

const counter = createCounter();

counter(); // 1
counter(); // 2
```

Mental model:

```text
createCounter()
      │
      ├── count = 0
      │
      └── returned function
              │
              └── remembers count
```

## 🔥 Callback vs Closure

|                           | Callback                                                         | Closure                                                 |
| ------------------------- | ---------------------------------------------------------------- | ------------------------------------------------------- |
| Meaning                   | Function passed somewhere to be called later/by another function | Function that retains access to its lexical environment |
| Example                   | `setTimeout(fn, 1000)`                                           | `() => console.log(name)`                               |
| Requires outer variables? | ❌ No                                                             | Usually involves captured outer variables               |
| Can be both?              | ✅ Yes                                                            | ✅ Yes                                                   |

Example:

```ts
const name = "John";

setTimeout(() => {
  console.log(name);
}, 1000);
```

Here the arrow function is:

```text
Callback → because it's passed to setTimeout
Closure → because it accesses `name`
```

## 🔥 Loop Closure Problem

| Code                          | Result  | Why?                                           |
| ----------------------------- | ------- | ---------------------------------------------- |
| `for (var i = 0; i < 3; i++)` | `3 3 3` | All callbacks share the same `var` binding     |
| `for (let i = 0; i < 3; i++)` | `0 1 2` | Each iteration has its own appropriate binding |

#### `var`

```text
One shared i
      ↓
callback 1 ──┐
callback 2 ──┼──→ i
callback 3 ──┘
               ↓
              3
```

#### `let`

```text
iteration 1 → i = 0 → callback
iteration 2 → i = 1 → callback
iteration 3 → i = 2 → callback
```

# 🔥 Deep Dive: Scope → Execution Context → Hoisting → TDZ → Closures

These concepts are connected. Don't learn them separately.

```text
JavaScript code
      ↓
Execution Context
      ↓
Lexical Environment
      ↓
Scope Chain
      ↓
Variable lookup
      ↓
Closures
```

## 1. Scope — "Where can I access this variable?"

Consider:

```ts
let name = "John";

function greet() {
  console.log(name);
}
```

`greet()` can access `name`.

Why?

Because `name` exists in an **outer lexical environment**.

Think:

```text
Global Scope
│
├── name
│
└── greet()
      │
      └── can look upward → name
```

But the reverse isn't true:

```ts
function greet() {
  const message = "Hello";
}

console.log(message); // ❌
```

Because:

```text
Global
  │
  └── greet scope
        └── message
```

The outer scope cannot look **inside** the inner scope.

## 2. Scope Chain ⭐

When JavaScript encounters:

```ts
console.log(name);
```

it has to answer:

> "Where is `name`?"

It searches outward.

```text
Current Scope
     ↓
Parent Scope
     ↓
Grandparent Scope
     ↓
Global Scope
     ↓
Not found → ReferenceError
```

Example:

```ts
const a = 10;

function outer() {
  const b = 20;

  function inner() {
    const c = 30;

    console.log(a);
    console.log(b);
    console.log(c);
  }

  inner();
}
```

`inner()` has access to:

```text
c → own scope
b → outer scope
a → global scope
```

This is the **scope chain**.

## 3. Lexical Scope ⭐⭐⭐

JavaScript uses **lexical scoping**.

That means:

> Scope is determined by **where the code is written**, not where the function is called.

Example:

```ts
const x = "global";

function outer() {
  const x = "outer";

  function inner() {
    console.log(x);
  }

  return inner;
}

const fn = outer();

fn();
```

Output:

```text
outer
```

Why?

Because `inner` was **defined inside `outer`**.

It doesn't matter that `fn()` is called elsewhere.

## 4. Execution Context ⭐⭐⭐

Now we go deeper.

Whenever JavaScript executes code, it creates an **execution context**.

For example:

```ts
const x = 10;

function greet() {
  const message = "Hello";
  console.log(message);
}

greet();
```

Conceptually:

```text
Global Execution Context
        │
        │ calls
        ↓
Function Execution Context
```

Every function call creates a new function execution context.

## 5. Call Stack

Execution contexts are managed using the **call stack**.

Example:

```ts
function a() {
  b();
}

function b() {
  c();
}

function c() {
  console.log("Hello");
}

a();
```

The stack evolves:

```text
a()
↓
b()
↓
c()
```

At the deepest point:

```text
┌──────────────┐
│ c()          │
├──────────────┤
│ b()          │
├──────────────┤
│ a()          │
├──────────────┤
│ global       │
└──────────────┘
```

`c()` finishes:

```text
c removed
 ↓
b()
 ↓
a()
 ↓
global
```

This is the **call stack**.

## 6. Hoisting

Now comes one of the most misunderstood concepts.

Consider:

```ts
console.log(x);

var x = 10;
```

Output:

```text
undefined
```

Not:

```text
ReferenceError
```

Why?

Because `var` declarations are processed before execution.

Conceptually:

```ts
var x;

console.log(x);

x = 10;
```

Important:

> **Declaration is hoisted, assignment is not.**

## 7. `let` and `const` Are Also Hoisted

This is where people often get confused.

```ts
console.log(x);

let x = 10;
```

You get:

```text
ReferenceError
```

Does that mean `let` isn't hoisted?

No.

`let` and `const` are also created during environment setup.

But they remain inaccessible until execution reaches their declaration.

That period is called the:

## Temporal Dead Zone

## 8. Temporal Dead Zone ⭐⭐⭐

Example:

```ts
console.log(x);

let x = 10;
```

Between entering the scope and reaching:

```ts
let x = 10;
```

`x` is in the **TDZ**.

Conceptually:

```text
Scope begins
     │
     ↓
   TDZ
     │
     │  x exists but cannot be accessed
     │
     ↓
let x = 10
     │
     ↓
x becomes accessible
```

So:

```ts
console.log(x);
```

throws a `ReferenceError`.

## 9. `var` vs `let` vs `const`

|               | `var`    | `let` | `const` |
| ------------- | -------- | ----- | ------- |
| Scope         | Function | Block | Block   |
| Hoisted       | Yes      | Yes   | Yes     |
| TDZ           | No       | Yes   | Yes     |
| Redeclaration | Yes      | No    | No      |
| Reassignment  | Yes      | Yes   | No      |

The key distinction:

```text
var
→ initialized as undefined

let/const
→ uninitialized → TDZ → initialized
```

## 10. Block Scope

`let` and `const` are block-scoped.

```ts
if (true) {
  let x = 10;
}

console.log(x); // ❌
```

The block:

```text
{
   let x
}
```

creates its own scope.

But:

```ts
if (true) {
  var x = 10;
}

console.log(x); // 10
```

`var` is function-scoped, not block-scoped.

## 11. Function Scope

```ts
function test() {
  var x = 10;
}

console.log(x); // ❌
```

`var` doesn't escape the function.

So:

```text
var
→ function scoped

let / const
→ block scoped
```

## 12. Closures ⭐⭐⭐⭐⭐

Now everything we've learned leads to closures.

Consider:

```ts
function outer() {
  const message = "Hello";

  function inner() {
    console.log(message);
  }

  return inner;
}

const fn = outer();

fn();
```

At first glance:

```text
outer() finishes
```

so you might think:

> "message should disappear."

But:

```ts
fn();
```

still prints:

```text
Hello
```

Why?

Because `inner` **remembers the lexical environment in which it was created**.

That's a closure.

## 13. Closure Mental Model

Think:

```text
outer()
 │
 ├── message = "Hello"
 │
 └── inner()
        │
        └── remembers outer scope
```

When `inner` escapes:

```text
inner
 ↓
closure
 ↓
retains access to outer lexical environment
```

So:

```ts
const fn = outer();
```

doesn't just return a function.

It returns something conceptually like:

```text
Function
+
Lexical Environment
```

## 14. Closure Example — Private State

Closures can create private state.

```ts
function createCounter() {
  let count = 0;

  return function () {
    count++;
    return count;
  };
}
```

Then:

```ts
const counter = createCounter();

console.log(counter()); // 1
console.log(counter()); // 2
console.log(counter()); // 3
```

But:

```ts
counter.count
```

doesn't exist.

The `count` variable is private to the closure.

## 15. Multiple Closures Have Separate State

This is extremely important.

```ts
const counter1 = createCounter();
const counter2 = createCounter();
```

Now:

```text
counter1
   ↓
count = 0

counter2
   ↓
count = 0
```

They don't share the same `count`.

Therefore:

```ts
counter1(); // 1
counter1(); // 2

counter2(); // 1
```

Each invocation of `createCounter()` creates a **new lexical environment**.

## 16. The Famous Loop Closure Problem

Consider:

```ts
for (var i = 0; i < 3; i++) {
  setTimeout(() => {
    console.log(i);
  }, 0);
}
```

Many beginners expect:

```text
0
1
2
```

But you get:

```text
3
3
3
```

Why?

Because `var` has one shared binding.

All callbacks close over the same `i`.

By the time the callbacks run:

```text
i = 3
```

So all callbacks see:

```text
3
```

## 17. Why `let` Fixes It

```ts
for (let i = 0; i < 3; i++) {
  setTimeout(() => {
    console.log(i);
  }, 0);
}
```

Now:

```text
iteration 1 → i = 0
iteration 2 → i = 1
iteration 3 → i = 2
```

Each iteration gets an appropriate binding.

Result:

```text
0
1
2
```

This is a perfect example combining:

```text
block scoping
+
closures
+
asynchronous callbacks
```

## 18. Closure ≠ Callback

Very important given our earlier discussion.

A **callback** is:

> A function passed to another function to be called later/by that function.

A **closure** is:

> A function together with access to its surrounding lexical environment.

They are different concepts.

This can be a callback:

```ts
setTimeout(() => {
  console.log("Hello");
}, 1000);
```

And that function is also a closure if it captures surrounding variables:

```ts
const name = "John";

setTimeout(() => {
  console.log(name);
}, 1000);
```

Here:

```text
callback → function passed to setTimeout
closure → function remembers `name`
```

A function can be **both**.
