Exactly — and this result gives us a **very useful surprise**.

PostgreSQL chose the **single-column index**:

```text
Bitmap Index Scan on idx_orders_user_id
```

even though the composite index:

```text
idx_orders_user_status(user_id, status)
```

could also theoretically satisfy `WHERE user_id = 8472`.

## Why?

Because for this query:

```sql
WHERE user_id = 8472
```

the `status` column provides **zero additional filtering**.

So PostgreSQL sees:

```text
idx_orders_user_id
    user_id
       ↓
    10 matches
```

versus:

```text
idx_orders_user_status
    user_id
    status
       ↓
    user_id matches
       ↓
    status isn't being used
```

The simpler index can be cheaper.

And notice:

```text
Execution Time: 0.128 ms
```

Still extremely fast. Don't optimize this further based on this tiny benchmark.

---

## But here's the real-world issue

We now have two indexes:

```text
idx_orders_user_id
idx_orders_user_status
```

The second one already starts with `user_id`.

Therefore, **the composite index can potentially replace the single-column index** for many `user_id` lookups.

But before deciding to drop `idx_orders_user_id`, we need to understand the trade-off.

### Every additional index has a cost

When we execute:

```sql
INSERT INTO orders ...
```

PostgreSQL has to maintain:

```text
orders table
     +
idx_orders_user_id
     +
idx_orders_user_status
```

Similarly, updates that modify indexed columns require index maintenance.

So unnecessary indexes mean:

* more disk space
* more write overhead
* more vacuum/maintenance work
* potentially more cache pressure

This is why **"add an index" isn't automatically a good optimization.**

# One more important experiment

Let's now test a query that is extremely common in real applications:

> "Give me the user's latest orders."

Run:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM orders
WHERE user_id = 8472
ORDER BY created_at DESC
LIMIT 5;
```

**Don't create an index for it yet.**

This is going to teach us something more interesting than the previous examples:

```text
WHERE
+
ORDER BY
+
LIMIT
```

We'll see whether PostgreSQL has to:

```text
find rows
    ↓
sort them
    ↓
take 5
```

or whether we can design an index that lets PostgreSQL essentially:

```text
find user
    ↓
already ordered by created_at
    ↓
take first 5
```

That is a **very common production optimization** for feeds, dashboards, order history, notifications, activity logs, etc.
