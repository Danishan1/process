Exactly. This is a **very clean demonstration of the leftmost-prefix rule for B-tree composite indexes**.

Your current plan:

```text
Seq Scan on orders
  Filter: status = 'PAID'
  Rows Removed by Filter: 74840
  Buffers: shared hit=899
  Execution Time: 5.982 ms
```

## 1. Why didn't PostgreSQL use `idx_orders_user_status`?

We have:

```text
idx_orders_user_status
    (user_id, status)
```

But the query is:

```sql
WHERE status = 'PAID'
```

The index is organized primarily by:

```text
user_id
   ↓
status
```

Conceptually:

```text
user_id = 100
    PAID
    PENDING
    CANCELLED

user_id = 101
    PAID
    PENDING
    CANCELLED

user_id = 102
    PAID
    ...
```

If PostgreSQL only knows:

```text
status = 'PAID'
```

it doesn't have a specific `user_id` section to jump into.

So the composite index isn't a good access path for this query.

Hence:

```text
Seq Scan
```

---

# 2. Look at the actual numbers

PostgreSQL estimated:

```text
rows=25193
```

Actual:

```text
rows=25160
```

That's **very accurate**.

So the planner isn't making a mistake.

The query returns:

```text
25,160 / 100,000 ≈ 25%
```

of the table.

That's also important.

Even if we create an index on `status`, PostgreSQL might decide a sequential scan is still cheaper because **one quarter of the table matches**.

This is a crucial lesson:

> An index existing does not mean PostgreSQL should use it.

---

# 3. Why `Seq Scan` actually makes sense here

You're reading:

```text
100,000 rows
```

and returning:

```text
25,160 rows
```

That's a lot of the table.

A sequential scan can simply walk through:

```text
page 1
page 2
page 3
...
page 899
```

and check:

```text
status = 'PAID'
```

Your execution:

```text
5.982 ms
```

is actually quite fast.

So **we should not automatically create an index just because we see `Seq Scan`.**

That's one of the biggest lessons from this exercise.

---

# 4. But let's test the index hypothesis

For learning purposes, create:

```sql
CREATE INDEX idx_orders_status
ON orders(status);
```

Then run the exact same query:

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM orders
WHERE status = 'PAID';
```

Now we have an interesting experiment.

There are two possible outcomes.

### Outcome A — PostgreSQL uses the index

Something like:

```text
Bitmap Index Scan
      ↓
Bitmap Heap Scan
```

because the index can identify the `PAID` rows.

### Outcome B — PostgreSQL STILL uses `Seq Scan`

And **that would also be a correct result**.

Why?

Because:

```text
25% of table matches
```

and PostgreSQL may determine:

```text
Sequential scan
     >
Index lookup + heap fetches
```

in terms of estimated cost.

---

## 5. This is where we move beyond "indexes"

We're now going to learn the much more important question:

> **At what selectivity does PostgreSQL prefer an index versus a sequential scan?**

There's no universal magic number like:

```text
"Below 10% → index"
"Above 10% → sequential scan"
```

It depends on:

* table size
* data distribution
* caching
* row width
* random I/O cost
* sequential I/O cost
* correlation
* visibility
* PostgreSQL cost parameters
* workload

And that's exactly the kind of reasoning expected at SDE-II level.
