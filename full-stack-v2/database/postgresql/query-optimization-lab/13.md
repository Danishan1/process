So unlike our previous `(user_id, status)` index, this index directly supports:

## 2. But look at the number of matching rows

out of:

# 3. Here's the interesting part

Look at:

```text id="q8hrzj"
Heap Blocks: exact=899
```

Our entire table occupies roughly:

```text id="yujzku"
899 heap blocks
```

And the bitmap heap scan touches:

```text id="7a8jvb"
899 / 899
```

**Basically the entire table.**

So the execution is effectively:

```text id="xq8n6e"
Index
  ↓
find 25,160 matching rows
  ↓
fetch rows
  ↓
touch almost every table page
```

The index helps identify the rows, but we still need almost all the pages.

# 5. This is the concept I want you to remember

### Highly selective query

```text id="h7k3fl"
100,000 rows
     ↓
10 match
```

Index can be extremely valuable:

```text id="1n6u3f"
index
 ↓
10 rows
```

### Low-selectivity query

```text id="c6v7n1"
100,000 rows
     ↓
25,160 match
```

Index doesn't magically eliminate the work:

```text id="o9d3u4"
index
 ↓
25,160 rows
 ↓
almost entire table
```

So the value of an index depends heavily on **selectivity**.

# 6. And this explains why PostgreSQL chose Bitmap Scan

This is actually a great example of why we shouldn't think only in terms of:

```text
Seq Scan vs Index Scan
```

PostgreSQL has another strategy:

```text
Bitmap Index Scan
        ↓
Bitmap Heap Scan
```

The bitmap is useful when there are **many matching rows**.

Conceptually:

```text id="6c9j9g"
Index Scan:

index → row
index → row
index → row
index → row
...

potentially lots of random heap access
```

Bitmap:

```text id="0p6r2k"
index
  ↓
collect matching page locations
  ↓
organize them
  ↓
fetch heap pages efficiently
```

That's exactly what you're seeing.

# 7. One subtle thing in your output

You have:

```text id="jz9t9v"
Buffers: shared hit=899 read=23
```

Don't say:

> "The query read 922 table pages."

That's not quite right.

The important distinction is:

```text id="7b5w1x"
shared hit = already in PostgreSQL's shared buffers
shared read = had to read into shared buffers
```

So this particular execution needed 23 additional buffer reads, while 899 page accesses were cache hits.

And because our dataset is tiny, **cache state is significantly affecting these benchmark numbers**.

# 8. There's another SDE-II lesson here

Suppose your production query is:

```sql
SELECT *
FROM orders
WHERE status = 'PAID';
```

and someone says:

> "It's doing a Seq Scan. Add an index."

That's an incomplete diagnosis.

A better investigation is:

```text id="9n3c7h"
1. How many rows match?
2. What percentage of table?
3. How many heap pages are touched?
4. Is the query actually slow?
5. Is the table cached?
6. What's the workload/frequency?
7. Does the index reduce actual work?
```

In our case:

```text id="y0h4q3"
25% of table matches
899 heap blocks touched
~4 ms execution
```

So depending on the production workload, an index might not be worth its write/storage cost.
