### 1. The 64 bits

A double is divided into three parts:

```text
┌───────┬──────────────┬────────────────────────────────────────┐
│ Sign  │   Exponent   │              Fraction                  │
│ 1 bit │    11 bits   │               52 bits                  │
└───────┴──────────────┴────────────────────────────────────────┘
   63       62 ... 52                    51 ... 0
```

So:

| Part              |   Bits | Purpose              |
| ----------------- | -----: | -------------------- |
| Sign              |      1 | Positive or negative |
| Exponent          |     11 | Controls magnitude   |
| Fraction/Mantissa |     52 | Controls precision   |
| **Total**         | **64** |                      |

The actual precision is **53 significant binary bits**, because normal numbers have an implicit leading `1`.

---

### 2. The mathematical representation

For a normal number:

```text
value = (-1)^sign × 1.fraction × 2^(exponent - 1023)
```

`1023` is called the **exponent bias**.

For example, conceptually:

```text
5.0
```

in binary is:

```text
101
```

which can be normalized to:

```text
1.01 × 2²
```

So IEEE-754 stores:

```text
sign     = 0
exponent = 2 + 1023
fraction = bits representing .01
```

---

### 3. Why does `0.1 + 0.2 !== 0.3` in JavaScript?

This is one of the most important consequences.

Decimal:

```text
0.1
```

does **not** have an exact finite representation in binary.

Similar to how:

```text
1/3 = 0.333333...
```

cannot be represented exactly in decimal, `0.1` cannot be represented exactly in binary.

So JavaScript effectively stores approximations:

```text
0.1 ≈ ...
0.2 ≈ ...
```

and therefore:

```js
0.1 + 0.2
// 0.30000000000000004
```

This isn't a JavaScript bug. It's a consequence of **binary floating-point representation**.

---

### 4. Precision limit

Double precision gives approximately:

```text
15–17 decimal significant digits
```

JavaScript exposes the safe integer limit:

```js
Number.MAX_SAFE_INTEGER
// 9007199254740991
```

which is:

```text
2^53 - 1
```

Therefore:

```js
9007199254740991 + 1
// 9007199254740992

9007199254740992 + 1
// 9007199254740992  ← problem
```

At this magnitude, not every integer can be represented.

For exact large integers, JavaScript provides:

```js
BigInt
```

---

### 5. IEEE-754 also defines special values

It's not just normal decimal numbers.

It also defines:

```js
Infinity
-Infinity
NaN
+0
-0
```

For example:

```js
1 / 0
// Infinity

0 / 0
// NaN

1 / Infinity
// 0
```

### 6. Why you should care as a backend developer

This matters particularly when dealing with:

* **money / financial calculations**
* database numeric types
* IDs larger than `2^53 - 1`
* timestamps
* scientific calculations
* serialization between Node.js and other languages
* JSON APIs

For example, **don't blindly use `Number` for large database IDs**:

```js
const id = 9007199254740993;

console.log(id);
// 9007199254740992
```

The value has already lost precision.

Use:

```js
const id = 9007199254740993n;
```

or represent it as a string when communicating through APIs, depending on the system design.

### Interview-level definition

> **IEEE-754 double precision is a 64-bit floating-point representation consisting of 1 sign bit, 11 exponent bits, and 52 fraction bits, providing about 15–17 decimal digits of precision. JavaScript's `Number` type uses this format, which is why values such as `0.1 + 0.2` can have floating-point precision errors.**

Sure. Let's use a simpler example than `0.1 + 0.2`.

### Example: `13.25`

IEEE-754 stores `13.25` in binary.

#### 1. Convert to binary

Integer part:

```text
13 = 1101₂
```

Fraction:

```text
0.25 = 0.01₂
```

So:

```text
13.25 = 1101.01₂
```

#### 2. Normalize it

Move the decimal point so there is one `1` before it:

```text
1101.01
↓
1.10101 × 2³
```

So we have:

```text
Sign     = 0       (positive)
Exponent = 3
Fraction = 10101
```

#### 3. Store the exponent

IEEE-754 uses a bias of **1023**:

```text
3 + 1023 = 1026
```

`1026` in binary:

```text
10000000010
```

#### 4. Final structure

```text
Sign       Exponent          Fraction
  0       10000000010       10101000000...
 │             │                 │
 1 bit       11 bits           52 bits
```

The fraction is padded with zeros to reach 52 bits.

So conceptually:

```text
0 | 10000000010 | 1010100000000000000000000000000000000000000000000000
```

### The important idea

When the computer sees:

```js
const x = 13.25;
```

it isn't storing the characters `"13.25"`.

It's storing something equivalent to:

```text
sign × binary fraction × power of 2
```

In this case:

```text
1.10101₂ × 2³
```

And because `13.25` has an **exact binary representation**, it can be represented exactly as a double.

Compare that with:

```text
13.2
```

which **cannot** be represented exactly in binary, so the computer stores the closest possible double.

**Rule of thumb:** IEEE-754 is essentially **scientific notation, but in binary**, packed into 64 bits.
